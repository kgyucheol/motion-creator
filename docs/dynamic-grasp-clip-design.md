# 동적 파지 클립 · Unitree 기본 정책 리플레이 설계안

상태: 설계(미구현). 베이스는 motioncreator, 실행 참고는 robot-studio(`dashboard/runner.py`)와 g1-live-studio(`g1live/arm_sdk_writer.py`).

## 1. 목표와 범위

LeRobot으로 가져온 파지 모션(클립)을, **화면에서 물체 오브젝트를 옮기면 그 위치에 맞게 손 경로가 바뀌도록** 만든다.
그 결과를 **Unitree 기본 정책(로봇이 자체 모션 모드로 서 있고, 프로그램은 팔·허리 요(yaw)만 `rt/arm_sdk`로 구동)** 위에서 실제 로봇에 재생한다.

범위 안
- 물체 위치는 화면에서 수동 지정(오브젝트 드래그). 비전 입력은 이번 범위 밖이다.
- 클립 하나에 물체 하나를 묶는 "동적 클립", 해석 결과의 미리보기·도달 판정.
- 팔(14축)과 허리 요 재생, 사전 점검, 접근·정지·복귀·제어 해제.

범위 밖
- 다리·골반·허리 롤/피치를 포함한 전신 정책 재생(그건 기존 decoupled_wbc/GEAR-SONIC 경로).
- 재생 도중 물체 위치 실시간 추종(8절에서 단계별로 다룬다).
- 손가락(그리퍼) 개폐. 데이터가 있어도 이번에는 무시한다.

## 2. 핵심 아이디어

원본 클립은 그대로 두고, **원본 + 물체의 기준 위치 + 물체의 현재 위치**로 보정된 샘플을 매번 계산한다(저장하지 않는 파생값).

```
Δ = T_물체_현재 · T_물체_기준⁻¹                      (월드 좌표 강체 변환)
손 목표(t) = blend( 손_원본(t),  Δ · 손_원본(t),  w(t) )   위치는 선형, 회전은 slerp
보정 샘플(t) = 전신 IK( 손 목표(t), 자세 기준 = 원본 샘플(t), 양발 고정 )
```

`w(t)`는 0~1 가중치다. 접근 구간에서 0→1, 파지 구간에서 1, 놓는 구간에서 1→0으로 움직인다. 구간 밖은 w=0이라 **원본과 완전히 같고**, 앞뒤 클립·포즈와의 연결은 지금의 자동 전환이 그대로 처리한다.
w=1에서 `Δ · 손_원본`은 "물체에 대한 손의 상대 위치를 유지하며 물체와 함께 이동한 손"이다. 기존 `pose_adaptive_grasp.py`의 물체 상대 경로 재조준과 같은 원리이므로 그 로직(상대 경로 → 월드 목표 → `Robot.solve`)을 일반화해 쓴다.

## 3. 데이터 모델

클립 키프레임에 선택 필드 `dynamic`을 추가한다. 없으면 지금과 동일하게 동작한다.

```json
{
  "name": "pick cube 3",
  "samples": [[...36...]],
  "dynamic": {
    "object_id": "box-1",
    "reference_pose": { "position": [x, y, z], "quaternion_xyzw": [qx, qy, qz, qw] },
    "hands": ["left", "right"],
    "window": { "ramp_in_start": 40, "hold_start": 70, "hold_end": 130, "ramp_out_end": 160 },
    "freedom": "yaw_xyz",
    "waist": "free",
    "max_shift_m": 0.25
  }
}
```

- `reference_pose`: **시연 당시 물체가 있던 자리.** LeRobot 데이터에는 물체 정보가 없으므로 사용자가 정한다(5절).
- `window`: 클립 샘플 번호 4개. `ramp_in_start`~`hold_start`는 smoothstep으로 0→1, `hold_end`~`ramp_out_end`는 1→0.
- `freedom`: `yaw_xyz`(기본, 이동 + 수직축 회전만) / `full6d`. 물체가 기울어진 보정은 도달성이 크게 나빠져서 기본에서 뺀다.
- `waist`: `free` / `lock`. 허리가 로봇 쪽에서 근사 구현되므로 잠그면 팔이 더 정확해진다(기존 `lock_waist`와 같은 이유).
- `max_shift_m`: 기준 위치에서 이만큼 넘게 벗어나면 보정하지 않고 오류로 표시(기본 0.25 m, 기존 값과 동일).
- 파일에는 원본 `samples`만 저장한다. 보정 샘플은 `(클립 해시, dynamic, 물체 현재 위치)`를 키로 한 캐시다.
- 클립 제약(핀·파지 불가)은 그대로 둔다. 손 목표는 `dynamic` 해석 내부에서만 쓴다.

## 4. 해석 알고리즘 (`motioncreator/dynamic_clip.py`, 신규)

1. 입력: `Robot`, 클립, 물체 현재 위치(프로젝트의 `scene_objects`에서 `object_id`로 조회).
2. 원본 샘플의 손 TCP(`Robot.point`)를 구간 `[ramp_in_start, ramp_out_end]`에서 0.1초 간격으로 뽑는다.
3. 각 점에서 목표를 만든다: `Δ`와 `w(t)`로 위치 lerp, 회전 slerp.
4. `Robot.solve`로 풀고(양발·골반 고정, 손 위치·방향 목표, `posture_reference` = 해당 시점 원본 샘플, 직전 해를 시드로 연속 풀이) 팔·허리만 취한다. 다리는 원본 값을 유지한다.
5. 점 사이는 관절 보간으로 원본 FPS까지 채우고, 구간 밖은 원본 샘플을 그대로 쓴다.
6. 판정을 만든다: 점마다 TCP 오차(mm)와 방향 오차(°). 임계는 g1-live-studio의 고스트 판정과 맞춘다 — 도달(<3 mm·2°), 근사(<20 mm·10°), 불가(그 이상). 파지 구간(`hold`)은 도달이 아니면 경고, 불가면 해당 클립 해석 실패로 취급한다. 관절 속도 최댓값도 함께 계산한다(IK 해가 튀는 것을 잡는다).
7. 계산량: 클립이 28초라도 구간이 전체가 아니고 0.1초 간격이므로 풀이 횟수는 구간 길이에 비례한다. 풀이 한 번의 실제 시간은 아직 측정하지 않았다. 구현 첫 단계에서 측정하고, 느리면 미리보기용 거친 간격(0.2초)과 저장·재생용 촘촘한 간격으로 나눈다.

`compile_motion`(`motion.py`)은 클립을 컴파일하기 전에 `resolve_dynamic_clips`를 호출해 보정 샘플로 바꿔 끼우고, 판정은 미리보기 응답(`keyframe_times` 옆)에 `dynamic_report`로 싣는다. 물체를 옮길 때 앞으로 보이는 자동 갱신은 지금의 `follow_object` 파지 미리보기와 같은 경로(디바운스 후 `/api/preview`)를 쓴다.

## 5. 기준 위치 정하기 (사용자 흐름)

기준 위치가 가장 중요한 입력이다. 틀리면 물체를 옮기지 않아도 손이 어긋난다.

1. 가져온 클립을 선택하고 슬라이더를 **손이 물체를 잡는 순간**에 둔다.
2. 오브젝트를 그 손 사이에 놓는다(드래그). 보조 버튼 **"손 사이에 놓기"**: 두 손 TCP의 중점에 물체 중심을 두고 수직 방향은 현재 값을 유지한다.
3. **"이 위치를 기준으로"**: 물체의 현재 위치를 `reference_pose`로 저장한다.
4. 슬라이더로 **접근 시작 / 파지 시작 / 파지 끝 / 놓기 끝** 4개 지점을 찍는다(현재 슬라이더 샘플 번호를 저장).
5. 이후 물체를 옮기면 손 경로가 따라온다. 결과 칩이 도달·근사·불가를 보여 준다.

UI 위치는 지금 있는 하단 키프레임 도구 줄이다. 클립 선택 시 **동적 파지** 그룹을 추가한다(물체 선택, 기준 지정, 구간 4점, 해제, 결과 칩). 타임라인에는 4점을 표시한다.

## 6. 기존 클립·포즈 흐름과의 상호작용

| 동작 | 처리 |
|---|---|
| 분할 | 분할 지점이 `window` 안에 있으면 두 클립 모두 `dynamic`을 복사하되 구간을 각자의 샘플 번호로 잘라 맞춘다. 구간 밖 조각은 `dynamic`을 비운다. |
| 합치기 | 두 클립의 `dynamic`이 같은 물체·기준이면 구간을 이어 합치고, 다르거나 한쪽만 있으면 합치기를 막고 이유를 보여 준다. |
| 포즈로 변환 | **보정된 샘플**에서 포즈를 만든다(물체를 옮긴 상태가 포즈에 굳는다). 변환 후 `dynamic`은 제거되고, 메시지로 알린다. |
| 자동 분할 | 원본 샘플 기준으로 동작한다. `dynamic`이 있으면 위 분할 규칙을 따른다. |
| 앞뒤 전환 | 구간 밖 w=0이라 끝점이 원본과 같다. 파지를 쥔 채 클립이 끝나는 경우(`ramp_out_end`가 마지막 샘플)는 다음 항목으로 가는 전환 시간이 자동 계산되므로 부드럽게 이어진다. |
| 저장·열기 | `dynamic`은 프로젝트에 저장된다. 맵만 따로 저장할 때는 물체 위치가 빠지므로 불러오면 기준 위치와 현재 위치가 같아진다(보정 없음). |

## 7. 검증 (테스트)

- Δ = 항등 → 보정 샘플이 원본과 같다.
- 물체를 +x로 0.05 m 이동 → `hold` 구간 손 TCP가 `Δ · 원본` 목표에 3 mm 안으로 들어온다.
- 구간 경계에서 보정 샘플이 원본과 연속(경계 오차 < 1e-6 rad).
- `max_shift_m` 초과, 도달 불가 → 판정과 오류 메시지.
- 분할·합치기·포즈 변환의 `dynamic` 처리.
- 실데이터 확인: robot-studio `pick cube` 에피소드로 기준 지정 → 물체 이동 → 판정 수치와 TCP 오차를 기록한다(화면 확인은 사람이 눈으로 한다).

## 8. Unitree 기본 정책 리플레이

### 8.1 정의와 제약

로봇은 Unitree 모션 모드(기본 균형·보행 제어)로 서 있고, 프로그램은 `rt/arm_sdk`로 팔을 구동한다. 가중치 `motor_cmd[29].q`(`kNotUsedJoint0`)를 0→1로 올리면 팔 제어권이 프로그램으로 넘어가고, 1→0이면 돌아간다. robot-studio는 허리 요(인덱스 12)도 같은 명령에 합쳐 보낸다. 따라서 이 경로로 재생되는 것은 **팔 14축 + 허리 요**뿐이다.

→ motioncreator에서 컴파일한 모션 중 다리·골반 높이/기울기·허리 롤/피치를 바꾼 부분은 이 방식으로 재생되지 않는다. 재생 전 점검이 이를 감지해 알린다(8.4).
→ 허리 롤/피치를 `arm_sdk`로 보낼 수 있는지는 로봇에서 확인되지 않았다. 기본은 허리 요만 보내고, 롤/피치가 0이 아니면 경고한다.

### 8.2 구조 — 프로세스 분리

robot-studio처럼 로봇 SDK를 쓰는 코드는 별도 자식 프로세스(로봇 Python, `unitree_sdk2py`)에 둔다. 서버(FastAPI)는 SDK를 import하지 않는다.

```
브라우저 ──ws/http──▶ motioncreator 서버 ──stdin JSON 줄──▶ replay_worker (로봇 Python)
   ▲                       │  재생 계획·점검·tau 계산            │ DDS rt/lowstate 구독, rt/arm_sdk 발행
   └── 진행·상태 ◀─────────┴──────── stdout JSON 줄 ◀───────────┘
```

워커 프로토콜은 g1-live-studio `arm_sdk_writer`의 것을 따른다: `engage`(현재 자세 유지 + 가중치 0→1), `target {q[14], tau[14]}`(목표이자 하트비트), `release`(가중치 1→0 후 종료), 이벤트 `ready/engaged/released/error`. 침묵 시간이 워치독 한도를 넘으면 스스로 가중치를 0으로 내린다. 게인과 관절 표는 `unitree_lerobot`의 `G1_29_ArmController`와 같다.

구현 선택지

| 선택 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. robot-studio 위임 | 보정 결과를 LeRobot `data.json`으로 내보내 robot-studio로 재생 | 새 하드웨어 코드 없음, 검증된 경로 | 팔 14축만 전달(허리는 robot-studio 자체 옵션), 포트 8765 충돌(둘 다 기본 8765), 두 앱 왕복 |
| B. 워커를 motioncreator에 이식 (권장) | g1-live-studio `arm_sdk_writer` 약 200줄 + robot-studio의 재생 절차를 `motioncreator/replay/`로 가져옴 | 한 앱에서 끝남, `unitree_lerobot` 설치 불필요, 가짜 DDS로 테스트 가능 | 코드 중복(출처 커밋 기록, 변경 시 수동 동기화) |
| C. `unitree_lerobot` 직접 호출 | robot-studio `runner.py`와 같은 방식 | 원본과 동일 동작 | 무거운 의존성(Pinocchio, lerobot), 모놀리식 |

권장은 **A를 1단계 임시 경로, B를 본 구현**으로 두는 것이다. A는 `data.json` 내보내기만 있으면 되고 `lerobot_format.py`의 역변환으로 만들 수 있다.

### 8.3 재생 상태 기계 (robot-studio 절차를 따른다)

```
IDLE → CONNECTED(읽기 전용 구독) → PREFLIGHT → APPROACH → PLAY ⇄ PAUSED → RETURN → RELEASE → IDLE
                                      └ 어느 단계에서든 STOP/오류 → HOLD 또는 RETURN → RELEASE
```

- **APPROACH**: 측정 팔 자세에서 첫 프레임까지 smoothstep 5초. 첫 프레임이 측정 자세에서 0.35 rad 넘게 멀면 경고(g1-live-studio 기준값).
- **PLAY**: 컴파일된 모션을 재생 Hz로 송신. 일시정지 중에도 마지막 목표를 계속 보내 제어권을 유지한다.
- **RETURN**: 시작 자세 또는 팔꿈치 준비 자세로 복귀하고 **도달을 측정으로 확인**한 뒤에만 다음 단계로 간다. 도달하지 못하면 중단하고 제어를 해제한다(robot-studio의 `ReturnArrivalError`).
- **RELEASE**: 가중치를 25단계(약 0.5초)에 걸쳐 0으로 내리고 마지막 0을 송신한 뒤 발행기를 닫는다.
- 서버 시작만으로는 어떤 명령도 나가지 않는다. 실물 재생은 명시적 UI 동작 + 확인 창(요약: 클립 수, 길이, 최대 관절 속도, 동적 판정)을 거친다. `--read-only` 플래그는 API와 UI에서 실물 재생을 막는다.

### 8.4 사전 점검 (PREFLIGHT)

실패하면 시작하지 않는다.

1. 3초 안에 `rt/lowstate` 수신, 이후 2초 넘게 끊기면 재생 중단.
2. 컴파일 결과의 팔 14축이 모델 관절 한계 안, 유한값.
3. 프레임 간 속도로 구한 관절 최대 속도가 한도 이하(g1-live-studio `REPLAY_VMAX`). 한도를 넘으면 허용 가능한 재생 속도 상한을 제시한다.
4. 측정된 현재 팔 자세·복귀 자세도 한계 안.
5. **재생 가능성**: 다리·골반·허리 롤/피치의 변화량이 허용 오차 이내인지. 아니면 "이 모션은 기본 정책으로 재생되지 않는 부분이 있다"고 구체적으로 알린다.
6. **동적 클립 판정**: 파지 구간이 "불가"면 시작 금지, "근사"면 확인 창에 표시.
7. 반복 횟수, 재생 속도, 접근·복귀 포함 총 시간 계산.

### 8.5 중력 보상 토크

robot-studio는 Pinocchio IK 솔버의 `solve_tau`로 목표 자세마다 토크를 구해 `ctrl_dual_arm(q, tau)`로 보낸다. 이 방식을 그대로 쓰면 워커에 Pinocchio가 필요하다. 대안으로 서버가 MuJoCo 역동역학(속도 0)으로 **궤적 전체의 tau를 미리 계산해 배열로 넘기면** 워커는 가벼워진다. 두 값의 차이는 아직 비교하지 않았다. 구현 첫 단계에서 가짜 로봇이 아닌 실제 자세 몇 개로 Pinocchio 값과 비교하고, 허용 차이를 정한 뒤 선택한다. 그 전에는 Pinocchio 경로를 기본으로 한다.

### 8.6 동적 클립과의 결합 단계

| 단계 | 내용 |
|---|---|
| v1 | 시작 시점의 물체 위치로 한 번 해석해서 전체를 보낸다. 재생 중에는 변경 없음. |
| v2 | 클립 경계에서만 재계산. 다음 동적 클립이 시작되기 전에 물체 위치가 바뀌었으면 남은 모션을 다시 해석하고, 현재 송신 중인 구간은 건드리지 않는다. 새 구간은 마지막 명령 자세에서 시작하는 전환으로 이어 붙인다. |
| v3 (보류) | 비전이나 실시간 추종. 별도 설계가 필요하고, 다리를 제어하지 않는 이 방식에서는 TCP 보정(`TcpCorrector`)의 가정이 맞지 않는다. |

## 9. UI 요약

- 클립 도구 줄: **동적 파지** 그룹(5절).
- 하단 재생 막대: 기존 미리보기 재생과 별도로 **로봇 재생** 패널(연결 칩, 인터페이스 이름, 재생 속도, 시작/일시정지/중단·복귀). 실물 시작은 확인 창을 거친다.
- 재생 중 단계 강조는 기존 `keyframe_times` 기반 강조를 재사용한다. 진행 위치는 워커가 올려 주는 현재 프레임 번호로 맞춘다.
- 점검 결과는 시작 전 모달에 항목별(통과/경고/실패)로 보여 준다.

## 10. 구현 순서

1. `dynamic_clip.py` + 모델/검증 + 테스트. 실데이터로 도달 판정 확인.
2. 프런트: 동적 파지 그룹, 구간 마커, 결과 칩, 분할·합치기·변환 규칙.
3. 재생 가능성 점검(8.4-5)과 보정 모션에서 팔+허리 요를 뽑는 함수. 내보내기 A 경로(`data.json`).
4. `replay_worker`(가짜 DDS 모드 포함) + 프로토콜 테스트 + 워치독·해제 테스트.
5. 서버 엔드포인트와 상태 기계, 사전 점검, UI 패널. 가짜 로봇으로 전 구간 확인.
6. 실물 시험은 로봇을 거치대에 매단 상태에서 작은 이동부터 사람이 직접 진행한다. 코드·테스트·스크립트에서 실물 재생을 시작하지 않는다.
7. v2(경계 재계산).

## 11. 열린 질문 / 위험

- **기준 위치 정확도**: 시연에 물체 위치 기록이 없어 사용자가 눈으로 맞춘다. 손 사이에 놓기 보조가 있어도 수 mm~cm 오차가 생긴다. 여러 시연이 같은 물체 위치였다면 같은 기준을 재사용하는 저장 기능이 필요할 수 있다.
- **IK 해 점프**: 연속 풀이와 자세 기준으로 줄이지만 보장하지 않는다. 속도 검사가 마지막 방어선이다.
- **허리 롤/피치의 `arm_sdk` 전송 가능 여부**: 실로봇에서 확인되지 않았다.
- **중력 토크 출처**(8.5), **풀이 시간**(4절 7항): 둘 다 측정 전이다.
- **코드 중복**: 이식한 워커는 g1-live-studio와 갈라질 수 있다. 출처 커밋을 문서에 남기고, 장기적으로는 공용 패키지 분리가 필요하다.
- **포트 충돌**: motioncreator와 robot-studio가 모두 기본 8765를 쓴다. A 경로를 쓰려면 한쪽 포트를 바꿔야 한다.
- 손가락 개폐는 범위 밖이므로 잡는 동작에서 손가락이 필요한 데이터는 팔만 재현된다.
